# JointCheck — remediation plan

This is future work, not an execution record. Preserve non-actionable abstention on the production route throughout evaluation; an owner-approved, isolated candidate may emit non-actionable research outputs only. [Review](REVIEW.md) defines findings and evidence. No test, deployment, hardware result or approval below is assumed to exist.

### T1 — establish safe baseline (JC-01, JC-04; prerequisite for all)

Observed paths: `README.md`, `backend/pyproject.toml`, `frontend/package.json`, `.github/workflows/ci.yml`. Steps: (1) record pinned SHA, toolchain, lockfile hashes and current limitations in a proposed baseline report; (2) in an authorized isolated environment, run the existing CI-equivalent backend, build and fixture checks using the observed scripts and record exit status, versions and failures separately; (3) exercise photo, gate and static fixture routes with synthetic, non-sensitive inputs and record whether all results remain non-actionable. Deliverable: reproducible baseline and defect ledger. Verification: a second reviewer repeats the documented procedure on the same revision. DoD: [ ] exact commands/results recorded; [ ] runtime versus historical CI distinguished; [ ] abstention observed, not assumed.

### T2 — reconcile domain contracts without enabling grading (JC-01, JC-02)

Prerequisites: T1 and qualified domain-owner participation. Observed paths: `backend/app/gate/gate.py`, `backend/app/vision/inspection.py`, `backend/tests/test_calibration_verdicts.py`, `schemas/core-schemas.json`, rules files. Steps: (1) map each proposed joint type, measurement, unit, calibration source, rule ID and class threshold to its actual schema and source, explicitly documenting gaps; (2) have qualified reviewers resolve definitions and trace authorized standards interpretations and versioned rule approvals, without claiming endorsement; (3) implement a provenance-bearing measurement interface and aligned contract only after review, retaining `UNDETERMINED` for missing segmentation, calibration, reviewed rules or trust. Deliverable: versioned contract, rule approval record and compatibility tests. Verification: malformed provenance, wrong units, missing masks and inconsistent class inputs abstain; a deliberately mismatched metric fails a non-mirrored integration test. DoD: [ ] reviewers sign definitions; [ ] synthetic tests distinguish unavailable from valid data; [ ] production grading remains disabled pending T6.

### T2a — authorize and isolate a candidate grader (JC-01, JC-02)

Prerequisites: T2 and explicit owner approval of the evaluation scope, datasets, access and safeguards; this is not approval to activate production grading. Proposed paths: a separate offline evaluation harness and candidate artifacts, locations to be chosen; no such implementation is claimed to exist. Steps: (1) specify the candidate's segmentation, calibration, measurement and reviewed-rule versions and freeze a traceable build and dataset manifest; (2) construct an isolated offline harness that runs the candidate on authorized inputs, marks every output research-only/non-actionable, and cannot publish verdicts to production routes, operators or assembly release systems; (3) independently verify the isolation and compare production route behavior before and during evaluation. Deliverable: owner-approved protocol, versioned candidate and isolation evidence. Verification: attempts to reach production or influence release from the harness fail, while `/v1/inspect` remains `UNDETERMINED` and `actionable: false`; a deliberately broken isolation control must fail its test. DoD: [ ] owner authorization recorded; [ ] candidate and data versions frozen; [ ] research outputs cannot trigger release/reject; [ ] production abstention independently observed.

### T3 — protect API, model sharing and compute (JC-03, JC-05; preventive security)

Prerequisites: T1, owner decides access, data classification and provider. Observed paths: `backend/app/main.py`, `backend/app/tf/vision.py`; proposed deployment gateway/configuration path to be selected. Steps: (1) threat-model anonymous access, authorization, image retention, logs, prompt injection and tenant separation; (2) enforce authenticated, authorized access and bounded per-principal request rate, concurrency, body size and cost at the chosen boundary; (3) bind bearer credentials to an approved TLS provider endpoint, explicitly authorize image sharing, redact sensitive logs and validate untrusted outputs. Deliverable: access/data-flow policy and implemented controls. Verification: staging negative tests reject unauthenticated and cross-tenant access, unapproved destinations, oversize/chunked images and concurrent floods; injected model text cannot cause actions or grading. Verify provider retention and contractual settings independently. DoD: [ ] secrets never printed; [ ] abuse controls measured under load; [ ] opt-in and off-switch proven.

### T4 — enforce meaningful automation (JC-04; dependent on T1, T2/T3 for their checks)

Observed paths: `.github/workflows/ci.yml`, `frontend/package.json`, `backend/tests/`. Steps: (1) add the existing `test:fixtures` script to CI using the compatible Node version and preserve backend/build checks; (2) add entry-point integration tests for abstention, opt-in sharing, invalid images, provider failure and correct UI disclosure; (3) add independent negative controls that deliberately break a guardrail or fixture expectation and confirm the intended check fails before restoring it. Deliverable: CI changes and mutation evidence. Verification: observe both a deliberately failing check and a restored successful run on the same proposed change; never equate count with coverage. DoD: [ ] fixture job is reachable; [ ] no skipped guardrail tests hidden; [ ] failures identify the broken behavior.

### T5 — release, recovery and user-facing safety (JC-03–05; preventive operations/UX)

Prerequisites: T3, T4 and owner hosting/retention decisions. Observed paths: `jobs/Dockerfile`, `frontend/src/App.tsx`; proposed runbook and accessibility test paths. Steps: (1) choose a supported release environment, pin and verify container/base dependencies and run with least privilege; (2) document monitoring, capacity limits, incident response, rollback and any necessary backup retention; (3) test static-fixture versus live-photo labeling, model-sharing consent, error states, keyboard access and screen-reader announcements with representative users. Deliverable: release/recovery runbook and UX evidence. Verification: deploy a versioned staging artifact, observe rollback and a restore of any retained state; if stateless, record that decision and verify configuration/secret recovery instead. DoD: [ ] rollback rehearsal observed; [ ] restore evidence or justified stateless recovery recorded; [ ] accessibility defects triaged with owners.

### T6 — independent domain acceptance (JC-01, JC-02; depends on T2a–T5)

Prerequisites: T2a's owner-approved isolated candidate, approved capture hardware, label access, qualified evaluators and predeclared acceptance criteria. Proposed deliverable: independent evaluation report. Steps: (1) collect representative authorized images across assemblies, joint types, cameras, operators, lighting and defect prevalence, with double-labelling and disagreement adjudication; (2) freeze dataset splits by assembly/source to prevent leakage and evaluate the versioned candidate through the isolated harness on held-out data, not through the currently always-abstaining production endpoint; (3) independently assess calibration, repeatability and traceable reviewed rules against physical references, then present unresolved failure modes to the owner. Report counts, denominators and uncertainty by defect, class and relevant capture subgroup. Verification: blinded evaluators reproduce metrics and audit failed examples, provenance, isolation and hardware setup; no synthetic or training-set score substitutes for held-out performance. DoD: [ ] acceptance thresholds agreed before evaluation; [ ] candidate and production outputs distinguished; [ ] physical and dataset limitations disclosed; [ ] owner records an evaluation go/no-go separately from any later production-activation approval.

For each predeclared evaluable, adjudicated joint or inspection unit, treat a reference defect as positive: candidate REJECT is a true positive (TP), ACCEPT a false negative/false accept (FN); for a reference non-defect, ACCEPT is a true negative (TN), REJECT a false positive (FP). Count `UNDETERMINED`, `PROCESS_INDICATOR`, missing outputs and errors separately as non-decisions, never as correct decisions; account for every eligible unit once. Report abstention/non-decision rate as non-decisions divided by all eligible units, including separate defective and non-defective denominators. Report decided-only sensitivity TP/(TP+FN) and specificity TN/(TN+FP), alongside coverage (TP+FN+TN+FP)/all eligible units; report false-accept rate FN/all reference-defective units, including defective abstentions in the denominator, and FN/(TP+FN) among decided defects. Report FN/(FN+TN) among all ACCEPT outputs as a separate predictive measure. Zero denominators are undefined, not zero. Stratify unusable and out-of-distribution cases and report exclusions with reasons and counts; do not silently drop failures or use abstentions to claim accuracy.

## Production acceptance and change control

- [ ] All safety, security, automation and recovery gates above have independently observed evidence; unknowns remain visible.
- [ ] Qualified domain owner approves intended use, target defect vocabulary, dataset rights, class-specific thresholds and residual false-negative risk; no certification is implied.
- [ ] Owner separately approves exposure, provider/data sharing, credentials, hosting, retention and release/signing. Offline candidate evaluation requires the explicit T2a authorization; any subsequent production activation or change from production abstention requires a distinct approval after T6, never implied by evaluation approval or a passing metric.
- [ ] Release immutable, traceable artifacts with migration/configuration version records. Roll back to the previously verified artifact and disable external model sharing or deployment if safety boundaries fail; verify actual service state after rollback. Preserve logs and data according to approved policy.
